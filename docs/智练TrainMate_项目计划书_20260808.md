# 智练 TrainMate 项目计划书

> 版本：V1.0
> 编制日期：2026-08-08
> 计划口径：以当前工作树为候选版本，不把代码存在、自动测试、模拟器、真机、签名和线上服务混为同一证据。
> 近期目标：先形成可复现、可验收的 iOS 内测候选版本；Android 商店发布与生产订阅不纳入本轮交付承诺。

## 1. 项目定位与原则

TrainMate 是一款本地优先的个性化训练应用：Flutter 负责 iOS、Android 与 Web 客户端，FastAPI 后端提供账号、赛事图片识别、受控 AI 产物、云端数据能力和订阅校验。

本计划始终遵循以下原则：

1. 健康、疼痛、身体指标与恢复判断优先在本机处理；涉及云端的健康字段必须单独征得同意。
2. AI 只能提出建议；画像、训练计划、周期重排等结果必须经用户确认后才生效，并接受本地安全规则复核。
3. 不以本地 Mock、测试替身、模拟器构建或功能开关存在替代真机、签名和线上验收。
4. 当前工作区已有大量未提交代码、素材和文档改动；在形成候选版本前，任何验收都必须绑定明确的提交版本与素材清单。

## 2. 截至 2026-08-08 的项目现状

### 2.1 架构与规模

| 维度 | 当前证据 | 结论 |
| --- | --- | --- |
| 客户端 | Flutter、GoRouter、6 个主导航入口、约 46 个生产路由、33 个页面文件 | 功能面较广，需以核心链路收口为先 |
| 后端 | FastAPI、PostgreSQL、Redis、Alembic；账号、赛事识别、AI、订阅等服务模块存在 | 具备预发布基础，但外部服务未完成线上验证 |
| 自动化测试 | 189 个 Flutter 测试文件、25 个后端测试文件 | 已有较大测试基础，当前客户端基线未全绿 |
| 数据与安全 | 本地优先存储、账号令牌与云同步边界、AI 结构化输出和安全审计均有代码与测试 | 高风险开关应继续保持关闭，直至独立验收通过 |

### 2.2 已具备代码能力

以下内容已在当前源码和既有文档中可见，但不等同于已上线：

- 今日训练、每日调整、四周训练计划、训练日详情、跟练播放器、训练日志与逐组记录。
- 动作库、动作替代与退阶、知识库、康复与疼痛红线、身体数据记录与趋势、周报和用户画像。
- 赛事导入与本地备赛、AI 训练对话、画像提议、受控训练处方、周期重排提议。
- 邮箱/手机号认证协议、赛事图片识别、AI 响应缓存、数据库迁移、账号导出和删除相关后端能力。
- iOS/Android 应用标识已统一为 `com.zhilian.trainmate`；iOS 订阅、健康档案云同步、首次引导等能力仍由开关控制。

当前 Flutter 失败已确认至少涉及三类回归：路由清单与断言数量不一致、动作媒体回退的展示行为与测试不一致、动作库引用的生成图片缺失。其余失败须在第一阶段逐项定位并登记；在根因与预期行为明确前，不以修改断言掩盖问题。

## 3. 近期目标、范围与非目标

### 3.1 近期目标

在冻结候选版本后，交付一个可在指定 iPhone 上完整体验下列核心闭环的 iOS 内测版本：

1. 登录或受控本地体验进入应用；
2. 完成首次资料与隐私同意流程；
3. 查看、生成或调整训练计划，并由用户确认后生效；
4. 执行一次跟练、记录结果并在本机恢复；
5. 访问动作库、赛事备战、身体数据和周报的核心入口；
6. 在不启用敏感云同步和付费生成门禁的前提下，验证退出、账号切换和本地数据边界。

### 3.2 本轮包含范围

- 清理当前客户端回归，建立全绿的静态分析与自动测试基线。
- 核验动作素材清单、媒体状态与页面回退规则，保证不把通用图或缺失文件包装为精确动作示范。
- 进行 iOS Simulator、真实 iPhone、通知、语音、HealthKit、离线恢复和账号切换的分层验收。
- 建立预发布后端环境，执行迁移、健康检查、认证和赛事识别的端到端验证。
- 形成可追溯的候选版本、验收报告、已知限制和回滚说明。

### 3.3 本轮不包含范围

- Android 正式签名、应用商店提交和旧包数据迁移；这些应在 Android SDK、正式 Keystore 和实机迁移方案到位后单独立项。
- 开启生产订阅、付费计划生成门禁、健康档案云同步或任何默认上传敏感健康字段。
- 扩展新的训练大功能、重写现有状态管理、替换框架或批量重构现有页面。
- 将外部训练 Skill 原文、未授权材料或未经审核的提示词加入运行时。

## 4. 实施路线与里程碑

时间使用 T+ 周表示：T 为产品负责人确认本计划、冻结本轮范围和指定候选提交的日期。实际工期取决于设备、账号、密钥和人员可用性；未取得这些外部条件时，里程碑顺延而不降低门禁。

| 阶段 | 建议周期 | 目标与主要工作 | 完成标准 |
| --- | --- | --- | --- |
| M0：候选基线冻结 | T+0～2 天 | 记录候选提交、工作树清单、路由和素材清单；将 9 个 Flutter 失败逐项归类为产品预期、代码回归或资源缺失 | 变更边界可复现；每个失败均有负责人、根因假设和修复验证方式 |
| M1：客户端质量收口 | T+3～7 天 | 修复或按已确认产品规则调整媒体、路由、动作库测试；消除静态分析提示；补足受影响测试 | `flutter analyze --no-pub` 与 `flutter test --no-pub` 全绿；无以删除断言、降级断言或伪造素材换取通过的改动 |
| M2：iOS 内测验收 | T+2 周 | 复建 Simulator 包；在真实 iPhone 走登录、权限、核心训练、离线恢复、退出和账号切换 | 指定设备、系统版本、步骤、预期与实际结果均进入验收报告；P0/P1 缺陷清零或获书面豁免 |
| M3：预发布后端联调 | 与 M2 并行，T+2～3 周 | 以独立预发布配置完成 PostgreSQL/Redis/Alembic、SMTP、短信、DeepSeek 与 MiniMax 的最小闭环 | `/readyz` 通过；迁移升级与回滚演练完成；真实密钥不进入仓库、日志或客户端 |
| M4：内测交付 | T+3 周 | 完成 iOS 签名、Archive/TestFlight 或指定 Ad Hoc 分发；输出已知限制、数据边界和回滚方案 | 测试人员可安装候选包并完成核心闭环；发布证据、版本号和候选提交一致 |
| M5：内测反馈与生产决策 | T+4～6 周 | 收集内测缺陷与使用反馈，判断是否具备生产发布条件 | 以质量、隐私、运维和商店门禁共同决策；不因功能齐全而跳过未完成门禁 |

## 5. 优先级工作包

### P0：质量与候选可复现性

| 编号 | 工作项 | 用户价值 | 验收标准 |
| --- | --- | --- | --- |
| P0-01 | 锁定候选提交与素材清单 | 每个测试结论都可复现，避免未提交改动混入内测 | 候选提交、依赖锁文件、素材清单、构建命令和验收环境已记录 |
| P0-02 | 收口 9 个 Flutter 失败 | 用户不会遇到入口、页面或媒体的已知回归 | 全量 Flutter 测试全绿；每项修复有对应回归测试 |
| P0-03 | 统一路由与页面矩阵 | 真实入口与测试预期一致，避免死链或漏验页面 | 路由数量与测试由同一清单或明确规则产生；新增入口均有导航与语义验证 |
| P0-04 | 修复动作媒体完整性 | 用户不会把缺失或通用素材误认为精准示范 | 每个动作引用文件存在，或明确标注为媒体占位/通用参考；资源来源与版权边界可追溯 |
| P0-05 | 清零静态分析问题 | 降低候选代码的低成本质量风险 | `flutter analyze --no-pub` 零问题；不引入新的 ignore 或全局豁免 |

**验收示例（P0-04）**

> 给定动作详情需要展示媒体，
> 当精确示范资源不存在时，
> 则页面必须展示明确的占位或通用参考状态，且不得显示“精确示范”的文案；测试应校验该状态和资源路径。

## 6. 发布门禁与决策规则

| 门禁 | 内测候选要求 | 未满足时的处理 |
| --- | --- | --- |
| 代码质量 | Flutter 分析和全量测试全绿；后端测试全绿 | 停止候选构建，优先修复或明确撤回本轮变更 |
| 素材与版权 | 运行时素材真实存在、状态准确、来源合规 | 移除引用或降级为明确占位，不得伪装为精确内容 |
| 数据与隐私 | 健康数据默认本地；云端和删除路径经独立验证 | 保持相关功能开关关闭 |
| 真机体验 | iPhone 核心链路、关键权限、离线恢复、账号切换通过 | 不进入 TestFlight/Ad Hoc 分发 |
| 后端预发布 | 迁移、就绪检查、关键外部服务与错误降级通过 | 仅允许本地演示，不可作为云端内测服务 |
| 分发与可回滚 | 签名、版本号、候选提交、已知限制、回滚方案齐备 | 不发布候选包 |

任何例外必须由产品负责人记录：例外项、用户影响、临时缓解、到期日期和复验责任人。涉及健康数据、账户、付费或删除操作的例外不得仅靠口头确认。

## 8. 建议的 Sprint 拆分

在未获得历史速度数据前，不预设故事点。每个 Sprint 只承诺不超过实际容量的 80%～85%，其余保留给回归与设备问题。

1. **Sprint A：质量基线**：P0-01 至 P0-05。目标是让当前候选版本的自动验证恢复全绿。
2. **Sprint B：iOS 内测体验**：P1-01 至 P1-04，与 P2-01 的预发布环境可并行，但必须在 P0 完成后才进入候选分发。
3. **Sprint C：预发布与分发**：P2-02 至 P2-04、P3-01。目标是完成受控 TestFlight/Ad Hoc 内测，而非生产全面开放。
4. **Sprint D：内测反馈**：只处理 P0/P1 缺陷、隐私问题与阻断性体验问题；新增功能进入后续 Backlog。

## 9. 项目度量与汇报

每周以同一模板汇报，至少包含：

- 候选提交、版本号、构建环境及变更范围；
- Flutter 分析/测试、后端测试、iOS Simulator、iPhone 真机、预发布服务各自的实际结果；
- P0/P1 缺陷数量、打开时长和回归状态；
- 动作素材完整率及“精确示范/通用参考/占位”分布；
- 内测核心链路完成率、崩溃/阻断反馈、隐私或权限异常；
- 已批准例外、外部依赖阻塞和下一周的门禁目标。

不将下载量、订阅转化、Token 降幅或运动效果列为本轮既成指标；在真实预发布/内测数据建立前，它们只能作为待测指标。

## 10. 完成定义

iOS 内测候选版本仅在同时满足下列条件时视为完成：

- [ ] 候选提交、依赖、素材与构建命令已固定并可复建。
- [ ] `flutter analyze --no-pub`、`flutter test --no-pub`、后端 `pytest` 均全绿。
- [ ] 动作媒体不存在未声明的缺失引用，且状态文案与实际资源一致。
- [ ] iOS Simulator 与指定 iPhone 的核心路径、关键权限、离线恢复和账号切换均有实测记录。
- [ ] 预发布环境迁移、就绪检查、认证和赛事识别最小链路通过；敏感数据与密钥边界复核完成。
- [ ] 测试人员能安装候选包，已知限制、隐私边界、回滚方案和问题反馈入口均已交付。
- [ ] 高风险功能开关的开启/关闭状态已复核，未验收能力保持关闭。

## 11. 需要产品负责人确认的决策

1. 近期目标是否确认限定为 **iOS 内测候选版本**，而非 iOS/Android 双端正式上架？
2. 对缺失的生成动作媒体，优先选择“补齐并核验授权”还是“先以明确占位/通用参考交付”？
3. 本轮内测是否完全排除订阅、健康档案云同步和付费计划生成门禁？
4. 可用于 iOS 真机验收的设备、系统版本、Apple 开发者账号和 TestFlight 分发方式分别由谁提供？
5. 预发布环境的 PostgreSQL、Redis、SMTP、短信、DeepSeek 和 MiniMax 的最小联调资源何时可用？

在以上决策未确认前，团队应只推进 P0 质量收口和不会改变数据/发布边界的验证工作。
