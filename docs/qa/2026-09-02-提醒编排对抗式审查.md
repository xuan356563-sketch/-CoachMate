## 4. 高优先级发现

### H1 页面上的六类提醒没有一条会真正推送

**证据**

- `lib/services/training_reminder_service.dart:99-110` 生成 `weekly-report` 提醒，`timeLabel: '周日 20:00'`。
- `lib/services/training_reminder_service.dart:63-81` 生成 `starter-program`，`timeLabel` 来自 `_starterReminderTime`（加班型用户硬编码 `21:30`）。
- `lib/features/reminders/training_reminder_page.dart:158-159` 把 `timeLabel` 与 `statusLabel` 并排渲染成「时间 / 状态」两行，`statusLabel` 在 `enabled` 时输出「已启用」（`lib/data/models/training_reminder.dart:50-52`）。
- `lib/services/system_training_notification_service.dart:116` 的 `_buildRequests` **只**遍历 `List<ScheduledWorkout>`，不接受也不读取任何 `TrainingReminder`。
- `grep` 确认 `buildReminders` 的唯一调用点是 `lib/features/dashboard/training_mvp_controller.dart:1297`，产物只进 UI 状态。

**影响**

用户在提醒编排页看到「周报提醒 · 时间：周日 20:00 · 状态：已启用」，合理预期是周日晚上会收到推送。实际上周日 20:00 什么都不会发生 —— 系统通知只会在 `ScheduledWorkout` 的时间点发出固定文案「训练提醒 / 打开 TrainMate 查看今日安排。」。恢复检查、轻松版确认、30 天引导这三类同理，其中 `recoveryCheck` 的 `timeLabel` 是「恢复倒计时结束前」、`proactiveDeload` 是「现在」，本身就不是可调度的时间值。

页面副标题写了「本地提醒 Mock」（`training_reminder_page.dart:21`），但卡片上逐条标注的「状态：已启用」直接与之矛盾 —— 免责声明和逐条状态在同一屏上互相拆台，用户会相信更具体的那个。

**建议**

三选一，不要维持现状：

1. 把 `TrainingReminder` 作为调度层的输入，让能确定时间的类型（`dailyPlan`、`weeklyReport`、`starterProgram`、`formalPlan`）真正进入 `TrainingNotificationScheduler`，无法确定时间的（`recoveryCheck`、`proactiveDeload`）明确标为「App 内提示」。
2. 若短期不做，把 `statusLabel` 从「已启用/已暂停」改为「App 内展示」，并在卡片上标出哪些会推送、哪些不会。
3. 最低限度：把不会推送的卡片的「时间」行去掉，避免给出可验证的虚假承诺。

### H2 通知点击后的 payload 无人消费

**证据**

- `lib/services/system_training_notification_service.dart:386` 训练通知写 `payload: '/daily-check-in'`。
- 同文件 `:410` 搭子通知写 `payload: request.payload`，内容为 `/companion?messageId=...`（`companion_notification_scheduler.dart:27-28`）。
- 同文件 `:422-436` 的 `_plugin.initialize(settings: ...)` **只传了 `settings`**，没有 `onDidReceiveNotificationResponse`，也没有 `onDidReceiveBackgroundNotificationResponse`。
- 全仓库 `grep onDidReceiveNotificationResponse|getNotificationAppLaunchDetails` 在 `lib/` 下零命中（除本文件自身外无任何注册点）。

**影响**

点击任何一条通知，只会把 App 拉到前台并停在上次的页面。搭子通知里精心编码的 `messageId` 完全不会被读取，用户点进去看不到那条消息。`Uri.encodeQueryComponent` 这层转义是在为一个不存在的消费者做准备。

**附带**：`ios/Runner/AppDelegate.swift` 的 `didFinishLaunchingWithOptions` 没有设置 `UNUserNotificationCenter.current().delegate`。这是 flutter_local_notifications 官方 iOS 接入步骤的一部分，缺失时 App 处于前台时通常不会展示通知，点击回调也拿不到 payload。这条需要真机验证后再改（不同插件版本的自动注册行为不同）。

**建议**

```dart
// _ensureInitialized() 内
await _plugin.initialize(
  settings: const InitializationSettings(...),
  onDidReceiveNotificationResponse: (NotificationResponse response) {
    final String? payload = response.payload;
    if (payload == null || payload.isEmpty) return;
    // 交给路由层；注意冷启动时 router 可能尚未就绪，需要缓存待处理深链
  },
);
```

冷启动路径还需要 `getNotificationAppLaunchDetails()`，否则「App 未运行时点击通知」这条最常见的路径仍然丢失。若短期不做深链，应把两处 `payload` 改成空串并删掉 `Uri.encodeQueryComponent`，避免留下看起来已实现的死代码。

## 5. 中优先级发现

### M1 夏令时转换当天提醒偏移 1 小时

**证据**

`lib/services/system_training_notification_service.dart:120-127`：

```dart
final timezone.TZDateTime dayStart = timezone.TZDateTime(
  location, workout.scheduledDate.year, workout.scheduledDate.month, workout.scheduledDate.day,
);
final timezone.TZDateTime scheduledAt = dayStart.add(Duration(minutes: minute));
```

`TZDateTime.add` 与 Dart 核心 `DateTime.add` 语义一致，加的是**绝对时长**（基于 epoch 毫秒），不是墙钟分钟数。跨越夏令时切换点时，结果的本地时刻会偏移。

以 `America/Los_Angeles` 2026-03-08（02:00 前跳一小时）为例：`00:00 PST + 450 分钟` 落在 `08:30 PDT`，而不是期望的 `07:30`。

**现有测试为什么没抓到**

`test/services/system_training_notification_service_test.dart:73-103` 的用例名为「跨夏令时按本地墙上时间调度固定提醒」，但取的两天是 **3/7 和 3/9** —— 转换日的前一天和后一天，恰好绕开了 3/8。两天各自内部都不跨越转换点，所以 `hour == 7` 成立，测试变绿。末尾断言两者 `timeZoneOffset` 不同，只证明了「测试确实横跨了夏令时」，没有证明「转换当天算得对」。这是一个名字比覆盖范围大得多的测试。

**验证用例**（请在有 Flutter 的机器上运行确认）

```dart
test('夏令时转换当天仍按本地墙上时间调度', () async {
  final gateway = _FakeTrainingNotificationGateway(location: location);
  await TrainingNotificationScheduler(gateway).synchronize(
    settings: _settings(enabled: true, followSchedule: false, preferredTimeLabel: '07:30'),
    workouts: <ScheduledWorkout>[_workout(DateTime(2026, 3, 8))], // 转换当天
    now: DateTime(2026, 3, 1),
  );
  expect(gateway.requests.single.scheduledAt.hour, 7);
  expect(gateway.requests.single.scheduledAt.minute, 30);
});
```

**建议**

改用墙钟构造，让 `timezone` 包自己处理转换：

```dart
final int hour = minute ~/ 60;
final int minuteOfHour = minute % 60;
final timezone.TZDateTime scheduledAt = timezone.TZDateTime(
  location,
  workout.scheduledDate.year,
  workout.scheduledDate.month,
  workout.scheduledDate.day,
  hour,
  minuteOfHour,
);
```

注意 `minute` 可能为负（见 L8），负值经构造函数规范化后会正确落到前一天，语义与现在一致。

中国大陆不使用夏令时，此问题只影响出境训练或时区设置在有 DST 地区的用户；但代码明确调用 `FlutterTimezone.getLocalTimezone()` 支持任意时区，不能靠「用户都在国内」来豁免。

### M2 并发同步会把用户刚保存的设置回退

**证据**

`lib/features/reminders/application/reminder_settings_controller.dart:146`：

```dart
if (!ref.mounted || state.settings.enabled != settings.enabled) return;
```

守卫只比较 `enabled` 一个字段。`:165-171` 的成功分支随后执行 `state = ReminderSettingsState(settings: settings, ...)`，其中 `settings` 是**闭包捕获的、发起本次同步时的旧值**。

**复现路径**

1. 用户把固定提醒时间从 `20:30` 改为 `07:30` → `setReminderTimeLabel` 保存并发起同步 A（携带 `leadMinutes: 30`）。
2. 用户立刻把提前量从 30 改为 15 → `setLeadMinutes` 保存并发起同步 B（携带 `leadMinutes: 15`）。
3. 两次 `enabled` 都为 `true`，守卫全部放行。
4. 若 A 晚于 B 返回，`state` 被写回 `leadMinutes: 30`。

**影响**

UI 显示 30，仓库里存的是 15，两者不一致。更糟的是下一次任意设置修改都从 `state.settings` 读取字段构造新对象（`:106-111`、`:120-125`），于是把用户设的 15 **静默写回 30** —— 用户的修改被无声吞掉，且没有任何提示。

**建议**

引入请求序号，只让最新一次同步有权写 state：

```dart
int _syncGeneration = 0;

Future<void> _synchronize(TrainingReminderSettings settings, {bool requestPermission = false}) async {
  final int generation = ++_syncGeneration;
  final result = await ...;
  if (!ref.mounted || generation != _syncGeneration) return;
  // 后续分支统一用 ref.read(repo).getSettings() 作为设置来源，而非闭包里的 settings
}
```

### M3 Android 权限判定把「未知」当「已授权」

**证据** `lib/services/system_training_notification_service.dart:300-304`

```dart
final bool? granted = await _plugin
    .resolvePlatformSpecificImplementation<AndroidFlutterLocalNotificationsPlugin>()
    ?.requestNotificationsPermission();
return granted ?? true;
```

iOS 与 macOS 分支（`:305-316`）在同样位置用的是 `?? false`。同一个方法里对「拿不到结果」给出两种相反的默认判断。

**影响**

`granted` 为 `null` 意味着插件解析失败或平台未返回结果。当成 `true` 后 `synchronize` 继续排程并返回 `scheduled`，控制器据此显示「已按本地时区安排 N 条系统训练提醒」。而在 Android 13+ 没有 `POST_NOTIFICATIONS` 时，`zonedSchedule` 不会报错，通知只是**永远不显示**。用户得到一个明确的成功承诺和零条通知。

**建议** 统一为 `?? false`；若担心旧版本 Android（13 以下无需运行时权限）被误判为拒绝，应显式按 SDK 版本分支，而不是用 `?? true` 覆盖所有情况。

### M4 冷启动路径从不检查权限就报「已安排」

**证据**

- `reminder_settings_controller.dart:57-59`：`build()` 中 `if (settings.enabled) unawaited(_synchronize(settings));`，`requestPermission` 取默认值 `false`。
- 同文件 `:48-56`：`workouts` 变化时的 `ref.listen` 回调同样不带 `requestPermission`。
- `system_training_notification_service.dart:76`：只有 `requestPermission == true` 时才会走权限检查，否则直接进入排程。

**影响**

用户在系统设置里关闭了 App 通知权限之后，每次冷启动都会「成功」排程并显示「已按本地时区安排 N 条系统训练提醒」。App 内没有任何路径能发现权限已被撤销 —— 状态文案是彻底的一面之词。

**建议** 在 `synchronize` 开始处查询当前授权状态（Android `areNotificationsEnabled()`、iOS `checkPermissions()`），未授权时返回一个新的 `permissionMissing` 状态，文案改成可操作的提示（例如「系统通知权限已关闭，点击前往系统设置开启」）。

### M5 权限被拒后文案与行为矛盾

**证据** `reminder_settings_controller.dart:150-164`

```dart
case TrainingNotificationSyncStatus.permissionDenied:
  final disabled = ref.read(reminderSettingsRepositoryProvider).saveSettings(
        TrainingReminderSettings(enabled: false, ...),
      );
  state = ReminderSettingsState(
    settings: disabled,
    statusMessage: '系统通知权限未开启，已保留设置并回退为应用内提醒。',
  );
```

**影响**

- 文案说「已保留设置」，实际把 `enabled` 写盘为 `false`。设置没有被保留，开关被永久关掉了。
- 文案说「回退为应用内提醒」，但如 H1 所述，App 内并不存在任何会主动触发的提醒机制。
- 由于 `build()` 只在 `enabled == true` 时才尝试同步（`:57`），用户即使事后在系统设置里授予了权限，App 也不会自动恢复 —— 必须手动再点一次开关，而界面上没有任何线索提示这一点。

**建议** 二选一：保持 `enabled` 不变、只改文案为「系统通知权限未开启，提醒暂时不会送达」；或者继续关闭开关，但文案如实说「已关闭提醒开关，授予权限后请重新开启」。

## 6. 低优先级发现

### L1 「通知里显示详细内容」开关无效

`companion_feed_page.dart:608-609` 的开关文案是「通知里显示详细内容 / 打开后，通知内容会显示在锁屏上，可能被旁人看到。」

但 proactive 消息的唯一写入点 `companion_controller.dart:539-540` 把两个字段硬编码为：

```dart
notificationTitle: 'TrainMate',
notificationBody: '你的搭子有话说',
```

于是 `companion_notification_scheduler.dart:17-21` 的两个分支实际输出为：

- 中性分支：`TrainMate` / `你的运动搭子有一条新消息。`
- 非中性分支：`TrainMate` / `你的搭子有话说`

两条都不含任何用户数据。开关的唯一效果是在两句同样中性的话之间切换，`?? '衡衡狸'` 这个 fallback 永远不会触发。

隐私方向上这是**安全的**（保守失败），但 `resolveCompanionPrivacy → privacyLevel → neutral` 这整条分级链路在通知层没有任何可观察效果，属于「看起来在防护、但防护对象不存在」。开关文案则明确承诺了不存在的行为。建议要么让详情真正生效，要么把开关文案改成实情。

### L2 关闭详情开关不影响已排期通知

`privacyLevel` 在消息创建时由仲裁器冻结（`companion_arbitrator.dart:112-115`）。`updatePreferences` 末尾调 `refresh()` → `_load`，而 `_load:509-512` 判断当天已有 proactive 消息时**不会重新仲裁**，只用旧 `privacyLevel` 重排通知。

当前因 L1 无实际危害，但 L1 一旦修复让详情生效，这条立刻升级为隐私缺陷：用户关掉开关后，当天已排期的通知仍会在锁屏上显示详情。修 L1 时必须同时处理 —— 关闭开关应触发已存消息的 `privacyLevel` 重算或强制降级为 L0。

### L3 `inexact` 调度与「提前 X 分钟」的承诺冲突

`setLeadMinutes` 的状态文案是「将在训练开始前 $value 分钟提醒。」（`reminder_settings_controller.dart:125`），而调度用的是 `AndroidScheduleMode.inexactAllowWhileIdle`（`system_training_notification_service.dart:385`）。Doze 模式下可能延迟数分钟到数十分钟，`leadMinutes` 下界是 15 分钟（`reminder_settings_repository.dart:46` 的 `clamp(15, 60)`），迟到的提醒完全可能在训练开始之后才响。

用 inexact 换取不申请 `SCHEDULE_EXACT_ALARM` 是合理取舍（manifest 里确实没申请这个权限），但文案应弱化为「大约提前 X 分钟」。

### L4 Android 小图标用彩色 launcher 图

`AndroidInitializationSettings('ic_launcher')`（`:424`），且 `AndroidNotificationDetails` 未指定 `icon`（`:376-382`）。资源确实存在（各 mipmap 目录下都有 `ic_launcher.png`，不会崩），但 Android 5.0+ 的状态栏小图标只取 alpha 通道，彩色图会渲染成白色方块或糊块。应准备单色透明的 `ic_stat_trainmate` drawable 并显式指定。

### L5 通知文案与落地页不一致

训练通知 body 是「打开 TrainMate 查看今日安排。」（`:373`），payload 却是 `/daily-check-in`（每日签到页，`:386`）。即便 H2 的深链修好，点进去也不是「今日安排」。两者应对齐。

### L6 取消与重排非原子，失败时留下空档

`synchronize:93-96` 先 `cancelTrainingNotifications()` 再逐条 `schedule()`。若第 k 条抛异常，`catch` 吞掉并返回 `unavailable`，文案是「系统提醒暂不可用，已回退为应用内提醒，不影响训练计划。」

实际状态是：旧提醒**已经全部被取消**，新提醒只排上了 k-1 条。文案里的「回退」不存在（无 App 内兜底），「不影响训练计划」也只在字面意义上成立 —— 提醒本身正是这个功能的全部内容。建议至少在 catch 里区分「取消前失败」和「取消后失败」，后者文案应明确告知提醒已被清空。

另外 `catch (_)` 完全吞掉异常对象，线上排障时没有任何线索。建议保留一份可读的错误信息到状态或日志。

### L7 32 条上限没有滚动补充

`_maximumScheduledNotifications = 32`（`:14`），按时间取最近 32 条。每周 4 练约覆盖 8 周。重排只在 App 内 `workouts` 或设置变化时触发。

用户长期不打开 App 时，第 33 条之后的提醒永远排不上 —— 而这恰恰是「提醒用户回来训练」最需要生效的场景。这是本地通知的固有限制（iOS 硬上限 64 条挂起通知），但应作为已知边界写进 README，不要让人以为提醒能无限期覆盖。

### L8 `startMinute` 缺省 0 把提醒推到前一天深夜

`training_schedule.dart:104`：`startMinute: (json['startMinute'] as num?)?.toInt() ?? 0`。

当持久化数据缺这个字段时，`0 - 30 = -30`，提醒落在**前一天 23:30**。跨天提前量本身是合理设计（凌晨训练理应前一晚提醒），但把「数据缺失」静默变成「深夜打扰」不合理。建议缺省值改用一个安全的默认训练时段，或在 `_buildRequests` 里对异常早的时间点跳过并记录。

### L9 两个独立网关实例与注释不符

`reminder_settings_controller.dart:22` 和 `companion_controller.dart:41` 各自 `new SystemTrainingNotificationGateway()`。两个实例各自维护 `_initialized` / `_timezoneInitialized`，`initialize()` 会被调用两次。

`system_training_notification_service.dart:187` 的注释写「运动搭子通知与训练通知共享平台权限、时区和插件初始化」—— 底层 `FlutterLocalNotificationsPlugin()` 确实是单例所以不会真冲突，但「共享初始化」的描述与实现不符。建议提取成单个 provider 供两侧复用。

### L10 Web/桌面上关闭提醒显示错误状态

`_ensureInitialized`（`:414-421`）在不支持的平台抛 `UnsupportedError`。而 `synchronize` 的 `enabled == false` 分支（`:70-75`）也会先调 `cancelTrainingNotifications()` → 抛异常 → 被 `catch` → 返回 `unavailable` 而非 `disabled`。

结果：Web 上点「暂停提醒」，`toggleTrainingReminders` 刚设好的「提醒已暂停」会被异步覆盖成「系统提醒暂不可用，已回退为应用内提醒」。建议在关闭路径上对平台不支持的异常单独放行，仍返回 `disabled`。

### L11 搭子通知每条重复解析时区

`scheduleCompanion:393` 内部 `await loadLocalLocation()`，而 `CompanionNotificationScheduler.synchronize:240` 已经解析过一次。每条通知都重复走一次 `FlutterTimezone.getLocalTimezone()` 平台通道，并重复执行 `timezone.setLocalLocation()` 这个全局副作用。应把 location 作为参数传入。

### L12 通知 ID 哈希碰撞会静默丢消息

`_notificationId`（`:159-167`）用 FNV-1a 映射到 100 万的 ID 空间。32 条训练通知按生日问题约 0.05% 概率发生碰撞，碰撞时后排的通知会覆盖前一条（同 ID），静默少一条提醒。概率很低，但由于 ID 输入包含 `scheduledAt.toIso8601String()`，可以改用「排序后序号 + 起始 ID」这种无碰撞方案，成本更低且完全确定。

## 7. 已核对并排除的怀疑项

对抗式审查中提出但经代码/配置核对**不成立**的怀疑，一并记录以免后续重复排查：

- **设备重启后通知丢失** —— 不成立。`AndroidManifest.xml` 已声明 `RECEIVE_BOOT_COMPLETED`，并注册了 `ScheduledNotificationBootReceiver`（含 `BOOT_COMPLETED`、`MY_PACKAGE_REPLACED`、两个 QUICKBOOT action）与 `ScheduledNotificationReceiver`。
- **`ic_launcher` 资源缺失导致 initialize 抛异常** —— 不成立。虽然 manifest 的 app 图标已换成 `ic_trainmate_official_flow`，但 `ic_launcher.png` 在全部 5 个 mipmap 密度目录下都还在，`mipmap-anydpi-v26/ic_launcher.xml` 也存在。（着色问题另见 L4。）
- **`followSchedule: false` 时同一天多条重复通知** —— 不成立。`TrainingScheduleService._selectSlot` 通过 `usedDates` 保证同一周内每个日期最多排一场训练（`training_schedule_service.dart:55-67`），因此一天只会有一条 `ScheduledWorkout`。
- **`notificationDetailEnabled` 开关没有接进隐私判定** —— 不成立。它经 `resolveCompanionPrivacy(detailEnabled:)`（`companion_arbitrator.dart:125-134`）映射到 `privacyLevel`，链路是通的。问题出在终点被硬编码文案抹平（见 L1）。
- **`build()` 中 `unawaited(_synchronize(...))` 会在 provider 初始化完成前写 `state`** —— 不成立。`synchronize` 是 `async` 且首个网关调用即 `await`，控制权必然先交回 `build()`，`state` 赋值发生在初始化之后。
- **搭子通知在锁屏泄露健康数据** —— 不成立。实际送出的 title/body 恒为中性文案，不含疼痛、体重、睡眠等任何用户数据。方向上是保守安全的。
